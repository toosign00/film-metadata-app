# Film Metadata 디자인 전면 개편 명세

## 1. 목표

Film Metadata 앱을 `DESIGN.md`의 디자인 원칙과
`/Users/toosign/development/github/my-blog`의 시각 언어를 바탕으로 전면 개편한다.

블로그 화면을 그대로 복제하지 않는다. 두 프로젝트가 같은 브랜드 패밀리로
느껴지도록 색상, 타이포그래피, 여백, 헤어라인, 상호작용 문법을 공유하면서
Film Metadata는 3단계 작업에 집중하는 도구형 제품으로 유지한다.

이번 개편의 성공 기준은 다음과 같다.

- 파일 선택, 메타데이터 입력, 결과 다운로드의 3단계 기능은 유지한다.
- 사용자가 각 단계의 목적과 다음 행동을 즉시 이해할 수 있다.
- 장식용 이미지보다 사용자가 선택한 사진과 결과 사진이 먼저 보인다.
- 라이트 모드와 다크 모드가 같은 디자인 체계로 보인다.
- 데스크톱, 태블릿, 모바일에서 작업 밀도와 가독성이 유지된다.
- 기존 메타데이터 처리, 프리셋, 다운로드 로직에 기능 회귀가 없다.

## 2. 범위

### 포함

- 전역 색상, 타이포그래피, 모서리, 여백, 포커스 토큰 재설계
- 헤더와 3단계 진행 내비게이션 재설계
- 각 단계의 공통 인트로 구조 추가
- 파일 선택 화면 재배치
- 메타데이터 설정 화면의 균등 카드 그리드 적용
- 프리셋 도구 모음 재배치
- 결과 화면의 사진 중심 카드와 다운로드 행동 재설계
- 푸터 간소화
- 단계 전환과 상태 변화의 절제된 애니메이션
- 반응형, 다크 모드, 키보드 접근성 개선

### 제외

- 파일 처리 알고리즘 변경
- 메타데이터 스키마 변경
- 프리셋 저장 형식 변경
- ZIP 생성 및 개별 다운로드 방식 변경
- 새로운 상태 관리 라이브러리 도입
- 서버 업로드 또는 백엔드 기능 추가
- 장식용 필름 사진, 질감, 배경 이미지 추가

## 3. 디자인 방향

선택한 방향은 **하이브리드 에디토리얼**이다.

현재 앱의 3단계 작업 흐름은 유지하되, 큰 외부 카드 안에 모든 콘텐츠를 넣는
구조를 제거한다. 각 단계는 캔버스 위에서 다음 순서로 읽힌다.

1. 영문 단계 라벨
2. 한국어 작업 제목
3. 짧은 설명
4. 핵심 작업 UI
5. 이전 또는 다음 행동

작업 밀도는 **균형형**을 사용한다. 제목과 설명에는 충분한 여백을 주지만,
핵심 작업과 상태 요약은 가능한 한 첫 화면 안에 유지한다.

## 4. 브랜드와 문구

### 서비스명

헤더 워드마크는 `Film Metadata`를 사용한다.

### 언어

구조를 나타내는 짧은 라벨은 영어를 사용한다.

- `01 / SELECT`
- `02 / METADATA`
- `03 / EXPORT`
- `Preset`
- `Selected files`

설명과 행동 문구는 한국어를 사용한다.

- 이미지를 선택하세요
- 촬영 정보를 입력하세요
- 결과를 확인하세요
- 다음 단계
- 메타데이터 적용하기
- ZIP 다운로드

한국어 문구는 딱딱한 `~합니다`, `~입니다` 대신 자연스러운
`~해요`, `~예요` 어미를 사용한다.

- 카드 반경은 16~18px를 사용한다.
- 입력창과 작은 버튼 반경은 8~10px를 사용한다.
- 주요 행동 버튼은 pill 형태를 사용한다.
- 그림자는 결과 이미지 또는 꼭 필요한 부유 요소에만 제한한다.

## 6. 공통 화면 구조

### Header

헤더는 다음 요소만 포함한다.

- `Film Metadata` 워드마크
- 데스크톱의 짧은 브라우저 처리 안내
- 시스템 연동 테마 전환 버튼

헤더는 기능 설명이나 큰 페이지 제목을 포함하지 않는다.

### StepNavigation

헤더 아래에 얇은 가로 진행 바를 배치한다.

- `01 Select`
- `02 Metadata`
- `03 Export`

상태 표현:

- 완료: Action Blue 배경과 체크 아이콘
- 현재: 기본 텍스트색 배경과 단계 번호
- 비활성: 헤어라인과 약한 텍스트

기존 이동 가능 조건을 유지한다.

- 1단계는 항상 이동 가능하다.
- 2단계는 선택 파일이 있을 때 이동 가능하다.
- 3단계는 처리 결과가 있을 때 이동 가능하다.
- 처리 중에는 단계 이동을 막는다.

### StepIntro

각 단계는 동일한 인트로 구조를 사용한다.

- 영문 단계 라벨
- 한국어 제목
- 한두 줄 설명

이 구조는 재사용 가능한 공통 컴포넌트로 만든다.

### Footer

데스크톱에서는 다음 정보를 한 줄로 표시한다.

- 브라우저 처리 안내
- 저작권
- 이메일

모바일에서는 읽기 편하도록 두 줄로 접는다.

## 7. 1단계: 파일 선택

### 정보 구조

- `01 / SELECT`
- `이미지를 선택하세요`
- 지원 형식과 최대 파일 수 설명
- 업로드 영역
- 선택 파일 목록
- 파일 수, 총용량, 지원 형식 요약
- 다음 단계 버튼

### 데스크톱

업로드 영역과 파일 목록을 나란히 배치한다.

- 업로드 영역이 더 넓은 비율을 가진다.
- 파일 목록은 파일명, 크기, 처리 순서를 보여준다.
- 총 파일 수와 총용량은 목록 또는 하단 요약에 표시한다.

### 모바일

업로드 영역 아래에 파일 목록을 배치한다.
목록은 화면 전체를 과도하게 늘리지 않도록 최대 높이와 내부 스크롤을 사용한다.

장식용 샘플 사진이나 히어로 이미지는 사용하지 않는다.

## 8. 2단계: 메타데이터 설정

### 정보 구조

- `02 / METADATA`
- `촬영 정보를 입력하세요`
- 전체 파일에 같은 정보를 적용한다는 설명
- 프리셋 유틸리티 바
- 2x2 균등 카드 그리드
- 이전 이동과 메타데이터 적용 행동

### PresetToolbar

카드 그리드 위에 한 줄 유틸리티 바로 배치한다.

- 현재 프리셋 상태
- 저장
- 가져오기
- 내보내기

프리셋은 정보 카드와 같은 크기로 강조하지 않는다.

### MetadataCard

다음 네 카드를 동일한 시각 구조로 제공한다.

1. `01 / CAPTURE`: 촬영 날짜와 시간
2. `02 / CAMERA`: 제조사와 모델
3. `03 / LENS`: 렌즈, 초점 거리, 조리개
4. `04 / FILM`: 필름 정보와 ISO

각 카드는 다음 요소를 가진다.

- 영문 번호와 그룹 라벨
- 한국어 제목
- 짧은 설명
- 기존 입력 필드

큰 외부 컨테이너 안에 다시 카드를 넣지 않는다.

### 반응형

- 데스크톱과 태블릿: 2x2
- 모바일: 한 열 카드 스택

## 9. 3단계: 결과와 내보내기

### 정보 구조

- `03 / EXPORT`
- `결과를 확인하세요`
- 다운로드 방법 설명
- 결과 개수
- ZIP 다운로드 주요 버튼
- 처리 진행률
- 오류 목록
- 결과 이미지 그리드
- 메타데이터 수정으로 돌아가는 텍스트 버튼

### ImageCard

사진 중심 카드로 구성한다.

- 4:3 이미지
- 파일명
- 촬영일
- 개별 다운로드 행동

카메라, 렌즈, 필름, ISO 같은 상세 정보는 카드에 추가하지 않는다.

개별 다운로드는 데스크톱 hover에만 의존하지 않는다.
키보드와 터치 환경에서도 발견하고 실행할 수 있어야 한다.

### 그리드

- 1280px 이상: 4열
- 768px 이상 1280px 미만: 3열
- 480px 이상 768px 미만: 2열
- 480px 미만: 1열

## 10. 버튼과 입력 요소

### 주요 버튼

다음 행동에 Action Blue pill 버튼을 사용한다.

- 다음 단계
- 메타데이터 적용하기
- ZIP 다운로드

### 보조 버튼

- 프리셋과 파일 관련 도구: 흰색 또는 표면색 배경의 헤어라인 버튼
- 이전 단계 이동: 텍스트 버튼
- 위험 행동: 기존 destructive 토큰 유지

### 입력 요소

- 최소 높이 41~44px
- 기본 표면 또는 보조 표면 배경
- 1px 헤어라인
- 명확한 라벨
- 오류 텍스트와 `aria-describedby` 연결
- 키보드 포커스 시 2px 포커스 링

## 11. 상태와 오류

다음 상태를 시각적·의미적으로 구분한다.

- 파일이 없는 빈 상태
- 파일 선택 완료
- 메타데이터 처리 중
- 전체 성공
- 일부 파일 실패
- ZIP 생성 중
- ZIP 생성 실패

처리 중에는 중복 행동과 단계 이동을 막는다.
진행률과 현재 처리 개수는 `aria-live`로 알린다.

일부 파일이 실패해도 성공한 결과의 개별 다운로드를 유지한다.
ZIP 다운로드는 성공한 결과만 포함한다.
오류 목록은 실패한 파일명과 원인을 보여준다.

## 12. 접근성

- 모든 상호작용 요소는 키보드로 사용할 수 있어야 한다.
- 버튼과 입력 요소는 최소 44px 터치 영역을 목표로 한다.
- 색상만으로 완료, 현재, 오류 상태를 구분하지 않는다.
- 아이콘에는 텍스트 또는 접근 가능한 이름을 제공한다.
- 진행 내비게이션은 현재 단계에 `aria-current="step"`을 사용한다.
- 비활성 단계는 실제 `disabled` 상태를 사용한다.
- 라이트와 다크 모드에서 텍스트와 Action Blue 대비를 확인한다.
- `prefers-reduced-motion`에서는 단계 전환 애니메이션을 제거한다.

## 13. 애니메이션

애니메이션은 작업 이해를 돕는 수준으로 제한한다.

- 단계 전환: 짧은 opacity 변화와 최대 4px 수직 이동
- hover와 focus: 150~250ms 색상 전환
- 로딩: 기존 회전 아이콘과 진행률
- 결과 카드의 순차 등장 애니메이션은 사용하지 않는다.

## 14. 컴포넌트 경계

신규 또는 재구성 대상:

- `Header`
- `StepNavigation`
- `StepIntro`
- `FileSelection`
- `FileSummary`
- `PresetToolbar`
- `MetadataCard`
- `MetadataSettingsForm`
- `ResultsViewer`
- `ImageCard`
- `Footer`
- `Button`

기존 `useAppReducer`와 서비스 계층은 유지한다.
화면 컴포넌트는 기존 상태와 콜백을 props로 받아 표현만 담당한다.

단일 화면에서만 쓰이고 로직을 줄이지 못하는 추상화는 만들지 않는다.
`MetadataCard`처럼 반복되는 구조와 접근성 계약이 명확한 경우에만 공통화한다.

## 15. 데이터 흐름

1. 사용자가 파일을 선택한다.
2. 기존 `setFiles`가 정렬된 파일과 1단계 상태를 갱신한다.
3. 2단계에서 React Hook Form이 입력과 검증을 관리한다.
4. 기존 debounce를 통해 앱 설정 상태를 동기화한다.
5. 사용자가 메타데이터 적용을 실행한다.
6. 기존 `processFiles`가 결과 이미지와 오류를 생성한다.
7. 결과나 오류가 있으면 3단계로 이동한다.
8. 기존 개별 다운로드 또는 ZIP 서비스가 파일을 내려받는다.

이번 디자인 작업은 이 흐름을 변경하지 않는다.

## 16. 검증

### 자동 검증

- `pnpm check`

현재 저장소에는 별도 단위 테스트 러너가 없다.
스타일 개편만을 위해 새 테스트 프레임워크를 도입하지 않는다.
새로운 상태 판정 로직이 생기면 컴포넌트 밖의 순수 함수로 분리하고,
기존 도구로 검증할 수 없을 때만 테스트 도입을 별도 논의한다.

사용자 요청에 따라 `pnpm build`는 실행하지 않는다.

### 브라우저 검증

다음 조합을 확인한다.

- 데스크톱 라이트
- 데스크톱 다크
- 태블릿 라이트와 다크

## 17. Git Flow

- 기준 브랜치: `develop`
- 기능 브랜치: `feature/design-overhaul`
- 구현 위치: 별도 Git worktree
- `main` 직접 커밋 금지
- 커밋은 변경 유형에 따라 `style`, `refactor`, `ally`, `test`, `docs`로 분리
- 구현과 검증 완료 후 `develop` 대상으로 PR을 만들거나 승인 후 로컬 병합

## 18. 구현 순서 제약

구현 계획은 다음 의존성을 지켜야 한다.

1. 전역 토큰과 공통 레이아웃
2. Header, StepNavigation, StepIntro
3. 공통 버튼과 입력 스타일
4. 파일 선택 화면
5. 메타데이터 카드 그리드와 프리셋 바
6. 결과 갤러리와 이미지 카드
7. 푸터
8. 반응형, 다크 모드, 접근성 보정
9. 전체 브라우저 검증

각 단계는 기존 기능을 유지한 상태로 `pnpm check`를 통과해야 한다.
